# ランタイムのルール契約

正本は[統合ルール・裁定 v2.1](../../docs/rules/siege-zeke-rulebook-current.md)。2026-10-22に、本書の確定裁定を正本の1.2.1／4.3／4.7.1／6.3／6.6へ統合した。本書は実装・テスト向けの補足として残す。現在のコードがすべての仕様を満たしているという保証ではない。宣言済み効果の後入れ先出しと同時誘発の交互処理の関係は、正本7.1の確認事項を参照する。

## 決着判定（2026-09-07確定）

適用範囲はゲーム全体の全勝利条件。STD-048だけの例外処理にはしない。ルール本文1.2/1.2.1/4.7に従う。

1. 現在解決している効果1つを、その全文まで処理する。「相手に3ダメージ。その後〜」は後半まで同じ効果。効果内の必要な対象選択で中断しても、完了までは同じ処理単位とする。
2. 途中の状態を確定済みの勝敗として保存し、残りの効果を打ち切ってはならない。処理完了時点の状態で勝利条件を判定する。
3. Spは効果解決後に発動元をゴミ箱へ送る処理まで終えてから判定する。
4. 最初に勝利条件が成立した効果完了境界で結果を固定する。一方だけならそのユーザーの勝利、両者が同じ境界で成立すれば引き分け。途中の成立は固定せず、固定後の状態変化は結果を覆さない。
5. 結果固定とゲーム終了を区別する。固定後は新しいプレイ・発動宣言を受け付けず、固定前に宣言済みだった双方の効果と、その解決に必要な選択だけを最後まで処理する。双方の宣言済みスタックを解決し終えたらゲーム終了とする。
6. 未承諾の発動候補や単なる誘発待ちは宣言済みではない。固定後に新しく宣言・追加実行してはいけない。

効果内の必要な選択と、別効果の誘発待機を区別する。同一タイミングの待機一覧全体や、追加誘発の連鎖全体を一つの効果とみなしてはいけない。逆に、全文の途中のダメージ・ドローなど個々の操作を、それだけで効果完了とみなしてはいけない。
この規則は決着タイミングについての規則であり、配置上限など他のルール判定を一律に後回しにするものではない。

## 降参・続行不能（2026-11-05確定）

ルールブック1.2の「降参」（いずれかのユーザーが投了を宣言する）と「続行不能」（システムにより敗北と判定される）。切断負けは続行不能にあたる。

- 文豪「投了と切断はそれでOK」（推奨の「宣言済みの効果や選択待ちが残っていても、その場で対局を終える」を承認）。宣言済みの効果・選択待ち・解決中の処理は解決せず、その場で対局を終える。1.2.1の「固定後も宣言済み効果の解決を待つ」は、効果による決着の規則であり、降参・続行不能には当てはめない。
- 負けるのは宣言した（または切断した）ユーザー、勝つのは相手。結果固定と終了は同時に行い、`victory.finished` と `victory.finishReason`（`concede` か `disconnect`）に残す。イベントは `result_finished` 1つに `reason` を載せる（効果による決着の `result_locked` は出さない）。
- 文豪「投了・切断は負けにする」。効果がすでに結果を固定していた場合（宣言済みの効果の解決待ちを含む）も、降参・続行不能を宣言した（切断した）ユーザーの負け、相手の勝ちで終える。固定済みの結果（相手の負けや引き分けを含む）は置き換える。AGENTS.md の「固定後の状態変化は結果を覆さない」は効果・状態変化についての規則で、降参・続行不能はその例外にあたる。
- 降参は、どのユーザーも、自分の手番でなくても、選択待ちの最中でも、最初の手番の前でも出せる。終了済みの対局、チュートリアル・ラボ・サンドボックス（勝敗を持たないモード）では出せない。
- 続行不能は、サーバーだけが出せる（`submitRuntimeSystemForfeit`）。クライアントのコマンドとしては受け付けず、`system:` で始まるコマンドIDもクライアントは使えない。ジャーナルには `systemForfeit` として残る。
- 効果の途中でどこにも置かれていないカード（解決中のSp、デコード途中のカードなど）は、持ち主のゴミ箱へ置く。
- ルールの変更ではなく、決着の入口を足しただけなので RULE_VERSION は上げない。

## STD-048の適用例

- ターン開始時の規定ドローはルール通り処理し、その後に①を処理する。
- 場に出せなかった場合、①は発動しない。
- ①を処理した場合は①の全文完了時に決着判定する。そこで結果が固定されたら、後ろのターン開始時効果や追加誘発を新しく宣言しない。既に宣言済みの効果があれば、その処理だけを終えてゲーム終了とする。

## 個別カードの共通境界（STD-086／124／142／159）

- STD-086の任意選択は0枚を認める。1枚を選んだ場合は通常の破壊処理（破壊禁止・プロテクト・バックアップ等の置換を含む）で破壊成立を判定し、成立した場合だけ後半のダメージを処理する。選択完了まではSpのゴミ箱移動と決着判定を保留する。
- STD-124のLogin時Xは自分のゴミ箱の枚数を参照し、0／2／3／5／7／20の各閾値を累積適用する。5以上でスリープするのは相手Obだけであり、Codeは含めない。再Loginでもその時点のXを再計算する。
- STD-142の②は各ターン終了時、両ユーザーの表向きの各コピーが独立して起動を選べる。発動元自身の破壊が成立した後にだけ後半へ進み、両ユーザーの公開エリア全体から表向きの「聖樹」を任意選択する。サルベージ上限は選択枚数ではなく、破壊判定が成立した実数。破壊先が置換されても成立数へ含め、破壊禁止・プロテクト等で防がれたものは含めない。
- STD-159は表向きの間だけ自身を破壊不可にし、敵味方を問わず公開エリアのObの破壊成立を数える。裏向きでは破壊不可も誘発も適用せず、加算値はターンごとにリセットする。複数枚ある場合は各コピーが独立して加算する。

## 強制実行（2026-09-13確定）

- 強制実行は、カード効果が指定した対象領域のカードを、効果の操作者が実行ユーザーとして実行する共通処理。対象範囲と配置先は各カードの本文または実行経路が指定する。
- 強制実行では対象カードの実行メモリを支払わない。対象カードの所有者は移動後も変わらない。以後のログイン・付与・遅延効果は、その配置先と実行ユーザーを基準に処理する。
- STD-105は自分の手札のLyd-Obから1体を選び、自分のエリアへ実行する。選んだObの実行メモリは支払わず、STD-105自身の起動メモリは通常どおり支払う。
- Lyd-ObはLydであり、同時にObでもある。「Ob」の条件・対象・効果にはLyd-Obを含み、「Lyd-Ob」と限定された指定はLyd-Obだけを参照する。「Lydではない」「Lyd以外」はLyd-Obを除外し、「Obではない」「Ob以外」はLyd-Obを含むOb系すべてを除外する。

## 効果配置（2026-09-13確定）

- ドラッグ、デコード、生成など、本文が実行を指示しない効果による配置は通常の実行を経由しない。メモリ・シンボルを要求せず、ログインおよび実行時誘発を発生させない。
- これらは効果配置イベントだけを通知する。アクセスからのドラッグはUI上で`access_drag`として区別してよいが、実行イベントではなく、`card_placed`（`placementCause: access_drag`）に加えて他の効果配置と同じ`card_effect_placed`も通知する（「効果で配置された時」の誘発はドラッグでも起きる）。
- 本文が明示的に実行またはログインを指示する場合だけ、無料であっても強制実行または通常の実行経路を使う。
- ドラッグ・デコード・規定ドローの配置先は、配置するユーザーが空きマスごとに選ぶ（2026-11-05、文豪の指示「マスごと」）。選択肢は空きマス1つ（zone と slot）と、置くカードが Code のときだけ重ねる先のOb。ルールブックはこれらを「指定エリアへ効果配置」とだけ書き、エリア内のマスを誰がどう決めるかは書いていない。
- 強制の効果配置（ドラッグ・デコード・規定ドロー）：空きマスのないエリアは選べない。どちらのエリアにも空きがなく、重ねる先もないときは、選ばせずに強制配置の失敗として処理する（置かれるカードはエリアに入らずゴミ箱へ。ルールによる破壊で、ログアウトは誘発しない）。任意の効果配置（「…できる」で使うもの。STD-179・STD-142①・STD-102①）：置ける所がないときは、使う入口（確認・起動・選択）を出さない。（2026-11-05、文豪「強制効果の場合は空きなしは配置不可、手動で任意配置なら経路自体を閉じる」）
- 効果配置も配置したターンの攻撃制限を受ける（rulebook 攻撃宣言。2026-11-07、文豪の報告「デコードでゴミ箱から出したObがすぐ攻撃できる」）。ゴミ箱・手札・山札から実在のカードが入るときは共通の配置口（placeByMode）で配置ターンの印を立てる。[QA]は静的キーワードなら印を立てず、[コンタクト]の例外は印を見て処理する。生成カードは生成する効果が決めた値を使う（STD-105 は配置してスリープ、STD-122 は ATK5 以上で[QA]）。

## ターン時点の既定（2026-11-01確定）

- 本文に「自分」「相手」が付かない「ターン開始時」「ターン終了時」「次のターン開始時」は、どちらのユーザーのターンにも適用する（各ターン）。カードの操作ユーザーが効果の主語になる。
- 実装は、該当カードの共通指定（`eachTurn` の起動時点、`timing: "next_turn"` の遅延、ターン開始時誘発の相手条件なし）で表す。カードごとの分岐は持たない。
- 本文が「自分ターン」「相手ターン」と書くものは従来どおり片方だけで起きる。

## 実行の置換（2026-11-01確定）

- 「その実行を別のカードの実行に置換する」は共通の経路（core/execution-replacement.js）で処理する。置換できるScriptはカードモジュールの `executionReplacementSpec` で宣言する。カードごとの分岐は持たない。
- 実行は「実行する時」、つまりメモリを払う前・配置とログインの前に止める。置換できるScriptが設置されている時だけ、相手に起動の確認を出す。断れば元の実行をそのまま続ける。
- 起動した場合、元のカードの実行メモリは払ったものとして扱い、元のカードは `original` の指定に従って片付ける（STD-204は置換先のレイヤーにする。`trash` ならゴミ箱）。置換先のカードは、元の実行をしたユーザーが、元のカードを出そうとしていた場所へ実行する。置換先のメモリは追加で払わず、ログインと`card_executed`は置換先について起きる。元のカードの`card_executed`は出ない。
- 置換先の実行はさらに置換されない。

## レジストリからの実行の色シンボル（2026-11-05確定）

- レジストリのカードを実行する時、色のシンボルの確認は、実行宣言の時点のレジストリで行う。そのカード自身が出しているシンボルも数える（文豪「出せるようにする」）。レイヤードの素材（ルールブック「レイヤード」）と同じ考え方。
- 実装は、宣言時の確認（`canExecuteRegistryCard`）を通ったあと、カードがレジストリを出てからの実行では色を再確認しない（`executeRegistryCard`）。

## 攻撃宣言の代価と、失敗した宣言（2026-11-07確定）

- 攻撃宣言時に、決まった場所からカードを手札に加えるかを選び、加えなければ宣言に失敗するカード（STD-214）は、共通の「攻撃宣言の代価」で作る。カード側は `attackDeclarationCostSpec`（`{ source, count, faceUp }`。`source` は `registry` か `trash`）を書くだけ。処理は `core/battle.js` の `declarationCost`。
- 宣言のとき、条件に合うカード（`faceUp` なら表向きだけ）が `source` に1枚でもあれば、選択の窓を出す。`count` 枚まで選ぶか、何も選ばない（任意）。選んだら手札に加えて、攻撃を続ける（`registry_left` のイベントは、`source` がレジストリのとき）。何も選ばなければ、宣言は失敗する。候補が0枚なら、窓を出さずにそのまま失敗する。
- 失敗した宣言（文豪「それの失敗は攻撃宣言に失敗してるんで、起きなくていい」）では、`attack_declared` も、相手のアンブッシュの窓も、戦闘も、ダメージも、攻撃宣言終了時の誘発も起きない。
- 失敗した宣言のあと、攻撃しようとしたObはスリープする（文豪「失敗したObはスリープする」）。攻撃は行われていないので、「攻撃した」の印（`attackedThisTurn`、対象がObなら `attackedObThisTurn`）は立てない（`failAttack`）。再攻撃を止めるのはスリープ（5.0 の :256）。印を読むのは、強制攻撃の確認（`core/turn.js`）と「このターンに攻撃した」の条件（`source_attacked_this_turn`）で、どちらも、行われなかった攻撃を数えない形になる。
- 宣言が成り立ったあと（代価を払ったあと）に、攻撃したObが宣言時の処理（アンブッシュ、Script の窓など）で破壊された・場を離れた・攻撃できなくなったときは、攻撃宣言時の誘発（`attack_declared`）は起こす（文豪「攻撃宣言をした時にScriptなどで破壊であれば起こす」）。そのあとは戦闘もダメージも攻撃宣言終了時の誘発も起きない。実装は、宣言が成り立った時点でObに `declaringAttack` を持たせ、`attack_declared` を出すときに外す。出す前に攻撃を続けられなくなったとき、`attack()` の入口がここで出す。
- 誘発の順番: 宣言時の処理は、今の順番のまま（攻撃したObの代価 → 相手のアンブッシュ → `attack_declared` の誘発）。4.7 では、アクティブでないユーザーのアンブッシュは、アクティブユーザーの `attack_declared` の誘発のあとに来るはずだが、アンブッシュは宣言への応答として先に処理する今の順番を変えず、`attack_declared` の誘発をその後ろに足しただけ。順番の組み直しは、この修正に含めていない。

## ランダム移動（2026-11-01確定）

- 「自分または相手エリアのいずれかにランダムに移動」は、両ユーザーのフロント／バックのうち、今いる場所と上限に達した場所を除いたものから等確率で選ぶ。
- 相手エリアへ移ったカードは、所有ユーザーは変わらず（デッキに入れたユーザー）、移った先のユーザーが操作する。

## 宣言待機の例

ショックガン宣言 → STD-003宣言 → ショックガンの効果全文とゴミ箱への移動 → 勝敗固定 → 宣言済みSTD-003を解決 → 他の宣言済み処理もなくなったら終了。
割り込むのは宣言であり、STD-003の効果処理をショックガンの途中へ差し込むものではない。後から処理したSTD-003で、既に終わったゴミ箱への移動を遡及して変更しない。

## 個別実装監査の確定裁定（2026-09-11）

- STD-121：設置時のコストは、エリアの名前の異なる「情報管理端末」カード3枚を破壊すること。ゴミ箱内の3枚をBANする処理でも、設置後の起動コストでもない。通常の破壊判定・置換・誘発を通す。実装修正は別途検証する。
- STD-148：全角の`［if：相手ターン開始時］`は表記揺れであり、`[if:相手ターン開始時]`へ訂正する。条件起動の機会を省略しない。
- STD-231：対象Obの両隣を対象に処理する。片方または両方の対象が存在しなくても全体を不発にせず、存在しない側は対象不在として処理する。隣接枠が別カードで埋まっている場合も、その側は生成せずスキップする。空いている隣接枠だけに生成・配置し、別位置への振替や他カードの強制移動は行わない。
- STD-237：自身（STD-237）はランダム生成候補から除外する。生成したObの配置は実行ではなく、ログインを誘発させない（2026-09-11確定）。生成・効果配置のイベントだけを通知し、実行イベントを通知しない。配置上限は通常の強制配置規則に従う。

ログインは実行した時の効果であり、単に生成・配置しただけでは誘発しない。メモリを支払ったかではなく、本文が実行を指示しているかで区別する。無料でも明示的な実行やリログはこの生成配置とは別である。

この節は裁定の記録であり、4枚すべてのランタイム修正完了を意味しない。

## 弾倉の実行手順

`[弾倉:X]`を持つSpの実行前に使用確認を行う。使用する場合は自分のエリアにあるレイヤーからちょうどX枚を選び、すべてを消費してから実行メモリをX軽減する。使用しない場合はレイヤーを消費せず、通常の実行メモリを支払う。軽減後の実行メモリは0未満にならない。

## レイヤー消費

カードが消費・破棄するレイヤーの枚数だけを指定している場合、操作ユーザーがそのカードの積層内から指定枚数を任意に選ぶ。選んだレイヤーだけを指定先へ移動し、選ばなかったレイヤーの順序は維持する。現行ランタイムではSTD-085／096／097／102／195は1枚、STD-238は2枚を共通選択処理で指定する。

## 実装・検証の状態

全勝利条件は効果完了境界で共通判定し、`winner`互換値とは別に`victory.lockedOutcome`、`lockedAtEffectId`、`finished`を保持する。結果ロック中は新規プレイを拒否し、UIも`RESULT LOCKED`と`GAME FINISHED`を分離した。同時誘発スレッドでは解決中の宣言済み項目だけを終え、未宣言項目を取消して終了する。

独立した`declaredEffects`スタックへSTD-003を含む`[if:]` Scriptと、公開カードプールの`[レスポンス:X]`8種（STD-015／034／047／132／143／167／203／207）を接続した。`[if:]` Scriptは自分ターン中の処理待ちがないメインアクション時にも起動できる。ただしイベント対象を本文で参照するSTD-018／019／038／204は、対応イベントなしでは対象を補完せず起動不可とする。起動承諾時はコスト、発動元、対象とイベント情報を宣言として確定し、現在の効果全文と発動元処理を終えた後にLIFOで解決する。Response自身は効果と必要な選択を終えてからゴミ箱へ送る。Response由来ダメージは、同一ダメージで宣言済みのResponseをすべて解決した後に別の受付窓を開く。

ショックガンによる致死では、ショックガンのゴミ箱移動、勝敗固定、宣言済みSTD-003またはResponseの解決と発動元処理、ゲーム終了の順をunit／browser E2Eで検証する。攻撃中のアンブッシュ／攻撃対象変更と破壊置換は処理分類が異なるため、宣言待機へ混在させない。

必要な回帰観点:

- ダメージで条件を満たしても「その後」の処理が完了する。
- 効果内の選択待ちでは決着しない。選択後の効果完了時に判定する。
- 条件が途中で成立しても、終了時に不成立なら途中の成立を持ち越さない。
